# Supabase Database Migrations

How the ZYVORA schema reaches the production database, why the files look the
way they do, and what was verified before they were committed.

Supabase project: `ycqheltqwgkvxblsqqab` · production branch: `main`

---

## TL;DR

The schema the API already runs against, expressed as Supabase migrations.
Five files, applied in timestamp order. They reproduce the existing schema
exactly (142 columns, 18 foreign keys, all unique constraints), seed the
reference data the seed script depends on, stop the backend's own migration
runner from re-creating tables that now exist, add the 18 missing foreign-key
indexes, and deny the Supabase API roles with Row Level Security.

**Status: applied and verified.** All five migrations are in
`supabase_migrations.schema_migrations`, Render is connected, and the DB routes
that used to 500 now return 200. See [Deployment status](#deployment-status).

---

## Why Supabase migrations at all

The backend has its own migration runner — Kysely, over
`apps/api/src/db/migrations/001..006`. That still works and was not touched.
Supabase needs its own directory because it applies `supabase/migrations/*.sql`
to a database it tracks itself, in `supabase_migrations.schema_migrations`.

So there are two runners and one schema. Section
[Two runners, one schema](#two-runners-one-schema) covers how that is kept from
becoming a conflict.

The backend connects with `DATABASE_URL` as usual. No Supabase client library
was introduced, and the frontend still talks only to Express.

## Files, in application order

### 1. `20261018120000_zyvora_baseline_schema.sql`

The whole schema: 18 tables in dependency order, plus `uuid-ossp`.

Generated by reading the live schema out of `information_schema` and
`pg_indexes` on a database that had all six Kysely migrations applied — not
transcribed by hand from the migration sources.

It reflects the end state, including:

- **`products.stock_quantity` is absent.** Migration 005 dropped it.
  `inventory` is the single source of stock truth. The storefront was
  previously advertising 100 of everything because the seed wrote per-product
  stock to a column nothing read, and hardcoded 100 into `inventory`.
- **The two `addresses` indexes** from migration 006, including the partial
  unique index that is what actually stops two concurrent "make this my
  default" requests both succeeding.

**One baseline rather than six ported files.** Porting 001–006 one-for-one
would produce six files whose only job is to express one schema, and would
misrepresent the history — those six were authored against a local PostgreSQL
instance, not as a Supabase history. A single baseline reproducing the end
state is both more honest and easier to review.

### 2. `20261018120050_insert_reference_data.sql`

The 2 roles and 4 categories.

This one was **missing from the first draft and caught by testing.** See
[Finding 1](#finding-1-migration-001-inserts-reference-data-not-just-schema).

### 3. `20261018120100_reconcile_kysely_migration_ledger.sql`

Marks Kysely migrations 001–006 as applied. See
[Two runners, one schema](#two-runners-one-schema).

### 4. `20261018120200_index_foreign_keys.sql`

18 indexes on foreign-key columns that had none. See
[Finding 3](#finding-3-16-of-18-foreign-key-columns-had-no-index).

### 5. `20261018120300_enable_row_level_security.sql`

`alter table … enable row level security` on all 20 public tables. No policies.
See [Row Level Security](#row-level-security-keep-it-on).

## Findings

### Finding 1: Migration 001 inserts reference data, not just schema

The first draft of the baseline created every table correctly and applied
cleanly to an empty database. It was still wrong.

Migration 001 does two things: it creates the schema, and it **inserts** the two
roles and four categories. The seed script only *reads* categories to resolve
`category_id` for every product — it never inserts them:

```ts
// apps/api/src/db/seeds/seed.ts
const categories = await db.selectFrom('categories').select(['id', 'slug']).execute();
const catMap = new Map(categories.map((c) => [c.slug, c.id]));
```

A schema-only database therefore had `categories: 0 rows`, and `npm run seed`
died with a misleading error pointing at the wrong thing:

```
null value in column "category_id" of relation "products" violates not-null constraint
```

Reading the migration files did not surface this. Applying them to a fresh
database did.

The four slugs are a closed union — `categorySchema` in
`apps/api/src/routes/catalog.ts` enumerates exactly `car-flags`, `bike-flags`,
`accessories`, `gift-sets`. A fifth category added to the database would not be
queryable through the catalog endpoint.

### Finding 2: 16 of 18 foreign-key columns had no index

```
addresses.user_id            indexed     audit_logs.user_id       MISSING
cart_items.cart_id          MISSING     cart_items.product_id    MISSING
carts.user_id                MISSING     inventory.product_id     MISSING
order_items.order_id         MISSING     order_items.product_id   MISSING
orders.user_id               MISSING     payments.order_id        MISSING
product_images.product_id    MISSING     products.category_id     MISSING
refunds.payment_id           MISSING     reviews.product_id       MISSING
reviews.user_id              MISSING     shipments.order_id       MISSING
users.role_id                MISSING     password_reset_tokens    indexed
```

Postgres does not create these automatically. Two costs, both invisible until
the data grows:

- `ON DELETE CASCADE` / `SET NULL` must scan the child table to find matching
  rows, holding locks for the length of the scan. Deleting one user cascades to
  `addresses`, `carts`, `reviews`, `password_reset_tokens`.
- Joins driven from the parent side sequential-scan the child.

Two non-FK lookups are indexed in the same file because they are hot paths with
no index behind them: `carts.session_id` (every guest basket read) and
`orders.checkout_session_id` (how a returning shopper finds their order).

Purely additive — no column, constraint or behaviour changes, so it is safe
against a database that already holds data.

### Finding 3: `search_path` was load-bearing by accident

The backend's Kysely migrations use `uuid_generate_v4()` as the id default, so
the baseline uses the same expression. On Supabase, `uuid-ossp` is installed
into the **`extensions`** schema, not `public`:

```
search_path   = "$user", public, extensions
fn_schema     = extensions
```

So an unqualified `uuid_generate_v4()` resolves — but only because the session
`search_path` happens to include `extensions`. That is an incidental property of
the session default, not a guarantee. A migration runner with a different
`search_path` would fail halfway through with *"function uuid_generate_v4() does
not exist"*, leaving a half-built schema on the production database.

Fixed by pinning it in the baseline:

```sql
set search_path = public, extensions;
```

Tables are still created schema-qualified, so this cannot silently redirect
them.

## Two runners, one schema

`npm run migrate` is the documented way to set up a database, and it runs on
the boot of any fresh environment. Kysely tracks what it has applied in
`kysely_migration`.

Pointed at a Supabase-provisioned database it sees an **empty ledger**, decides
001–006 have never run, and tries `CREATE TABLE` on tables that already exist —
production fails at deploy time with `relation "users" already exists`.

So migration 3 seeds the ledger with the six migration names. The Kysely runner
then no-ops against a Supabase database, and still does its real work against a
fresh local one, where those rows do not exist.

**This is reconciliation, not suppression.** Every object marked applied
genuinely exists — migration 1 created exactly that schema, including the
effects of 005 and 006. `on conflict do nothing` makes it idempotent.

## Row Level Security: keep it on

### The problem it solves

Every table in `public` is reachable over PostgREST with the project's `anon`
key. That key is **meant** to be public — Supabase's own docs tell you to ship
it in browser bundles. It grants no rights by itself; **RLS is what grants
rights**. Without RLS on a `public` table, `anon` inherits full access.

This application does not use the Supabase API at all. That is not a control:

```
GET /rest/v1/users?select=email,password_hash     → every row
GET /rest/v1/audit_logs                           → the full audit trail
GET /rest/v1/password_reset_tokens                → Argon2id hashes of live reset tokens
```

`users.password_hash` and `password_reset_tokens.token_hash` are both in reach.

### Why it does not break the backend

RLS does not apply to the table **owner**. Migrations run as `postgres` on this
project:

```
current_user = postgres
```

so `postgres` will own the tables, and the backend's `DATABASE_URL` connects as
`postgres` too. `FORCE` is deliberately **not** used.

Verified rather than assumed, on a throwaway table with RLS on and zero
policies:

| connection | result |
|---|---|
| owner (`inkyank-08`) | `reads: hunter2` — backend works |
| non-owner (`zyv_app`) | `reads:` nothing — everyone else denied |

### Verify it yourself, one minute

After the migrations apply:

```bash
# must return [] or 401 — never rows
curl "https://ycqheltqwgkvxblsqqab.supabase.co/rest/v1/users?select=email,password_hash" \
     -H "apikey: $ANON_KEY"
```

Then log into the app and load the catalogue. If that works, both halves are
proven: backend unaffected, anon key locked out.

### If it ever does break

Only if the backend connects as a non-owner role. The symptom is
`permission denied for table users`.

**Do not disable RLS and do not add a permissive policy** — either reopens the
hole. Instead exempt the backend role explicitly:

```sql
alter role <pooler_role> bypassrls;
```

RLS is a **separate, final migration** precisely so that a connection-role
problem surfaces against a working application rather than during the initial
deploy.

At the moment of commit, nothing had been applied to Supabase — every call

integration apply.

**The 220/220 run is the load-bearing result.** It is the whole schema,
migrated the way production will migrate it, then exercised by every existing
API test.

### Could not be executed

- The live PostgREST check with the real anon key. RLS mechanics were verified
  on a throwaway table — owner reads, non-owner denied — but the actual
  `curl /rest/v1/users?select=*` against the live project was not run, because
  the anon key is not available to the agent. **This is the one outstanding
  verification.**
- The GitHub App installation on this repository could not be confirmed —
  `GET /user/installations` returns 403 for a user token. The repo has no
  webhooks, which is expected (Supabase delivers via a GitHub App) but means the
  install status is not visible from here.
- `supabase db push` and `supabase migration list` were not run. No Supabase
  CLI is installed locally. Ordering and filename validity were checked by
  filename convention and by applying the files directly to a fresh database.

`list_tables` and `list_migrations` reported **0 tables and 0 migrations** at a
moment when 20 tables and 5 migrations already existed. Those tools are not
reliable for verifying schema state. Use `execute_sql` against

## Operations

### Connect the app

Point `DATABASE_URL` at the Supabase connection string. Use the **pooler**,
not the direct connection — the direct connection will exhaust connection
limits under load:

```
postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:5432/postgres
```

Port `6543` is the transaction pooler. Prefer `5432` (session mode) unless
prepared statements are disabled, because Kysely/pg uses them.

The password goes in the environment only. It is never committed, and never
reaches the frontend — the browser has no `DATABASE_URL`.

### Seed

**The GitHub integration does not run seeds.** Supabase ignores `seed.sql` by
default. Run it once by hand:

```bash
npm run seed -w @zyvora/api
```

It is idempotent by refusing to run when products already exist.

### Rollback

Each migration is additive, so there is nothing to roll back by dropping. To
revert a schema change, write a new migration — Supabase has no `down`.

For the backend's own runner, `npm run migrate:down` rolls back the most
recently applied Kysely migration. It takes no argument on purpose: rolling
back by name invites pointing it at the wrong migration.

## Adding a future migration

1. Add the migration to `apps/api/src/db/migrations/00N_*.ts` first, with its
   `down()`.
2. Run it locally. Verify against `zyvora` — the live-shape database.
3. Create `supabase/migrations/<timestamp>_<name>.sql` mirroring the same
   change. Timestamps are `YYYYMMDDHHMMSS` and order is lexicographic.
4. Test by applying the whole `supabase/migrations/` directory to a **fresh**
   database. A migration that only works on an already-migrated database is not
   validated — that is how the reference-data gap survived review.
5. Push. Do not reuse an existing timestamp.

## Not in scope

These migrations reproduce the existing schema. They deliberately do not
introduce:

- **Supabase Auth.** The application has its own Express authentication —
  Argon2id password hashing, JWT session cookies, double-submit CSRF
  (`apps/api/src/auth`). `users` is the application's own table; it has a
  `password_hash` column, which is not a Supabase Auth table. Adding Auth would
  introduce a second, competing identity system.
- **Row Level Security policies.** RLS is enabled with zero policies on
  purpose — deny-all for the API roles. A permissive policy reopens the table
  and must be a deliberate, reviewed change.
- **Seed data.** No products. Supabase does not seed on deploy.
- **Edge Functions or Storage buckets.**
